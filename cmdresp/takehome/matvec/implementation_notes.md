# Implementation and integration notes

- The unmodified Waveflow scaffold passed its Python simulation baseline before adaptation.
- The first boundary-generation attempt reported `Stale impl file detected ... Hook 'body' is now non-templated; expected file is matvec_body_impl.cpp`. The stream declarations used literal width 32 rather than the declared `in_bw/out_bw` parameters. Connecting those parameters corrected hook discovery; no generated file was edited.
- Initial C simulation detected correct result values but missing final result TLAST. Waveflow's generated `int64_array_utils::write_axi4_stream_elem_impl<32>` explicitly casts `tlast` to void and writes both halves with false. The body now uses the generated `write_array_lane<32>` serializer and `streamutils::write_axi4_word<32>` to frame its two serialized words. This uses existing supported serializers, with no manual bit packing and no changes to generated output. The failing run is retained as `evidence/history/csim_01_missing_output_tlast.log`; the corrected C simulation checks all scenarios.
- Standard Vitis RTL co-simulation passed all 85 activations, but inspection of its generated adapter showed that only `port.depth = initSize - size_after_call` input beats were replayed. Thus its post-check of unread C++ stream data could not prove sentinel non-consumption at the physical interface.
- Added a single combined pin-level SystemVerilog suite, driving the complete queued stimulus and leaving sentinels VALID for at least 20 cycles after completion, with observed AXI-Lite status and all input/output handshakes recorded. The first run exposed two extra input handshakes per activation, caused by default AXIS input registers. The failing traces and statuses are retained in `evidence/history/rtl_registered_input/`.
- Applied `set_directive_interface -mode axis -register_mode off matvec s_in` in the hand-written HLS script to remove that functional read-ahead. Generated kernel/interface files are unchanged. This is a functional correction, not performance tuning. AMD documents the register-mode option in [UG1399](https://docs.amd.com/r/2024.1-English/ug1399-vitis-hls/set_directive_interface).
- The off directive was accepted and is recorded in `solution1_data.json` under `DirectiveTcl`, but synthesis still reports `axis (register, both mode)` and `csynth.xml` attributes the interface constraint to the generated pragma. The second synthesis therefore does not fix read-ahead. Waveflow's `waveflow/build/hwgen.py::kernel_signature` has no register-mode configuration hook: it emits the fixed AXIS pragma. Project instructions prohibit editing generated boundaries and require reporting an unexpressible interface instead of hand-editing it. The final report retains this as an Open Item. AMD documents that conflicting pragmas/directives can cause the later directive to be ignored in [Adding Pragmas and Directives](https://docs.amd.com/r/en-US/ug1399-vitis-hls/Adding-Pragmas-and-Directives).
- The pin-monitor cycle counter was moved into the same clocked block as handshake logging to remove simulator scheduling ambiguity; the final full-queue run uses that instrumentation. This changes only measurement code.
